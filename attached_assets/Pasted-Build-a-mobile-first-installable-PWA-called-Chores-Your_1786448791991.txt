Build a mobile-first installable PWA called Chores Your Own Adventure.

This is a family chore/task app wrapped in a retro fantasy RPG. Adults and kids complete real-life chores and responsibilities as “quests,” earn XP and Gold, level up persistent pixel-art characters, unlock equipment and pets, participate in shared Party Goals, and occasionally fight household “Bosses.”

The app should feel fun, lightweight, and fast. It should NOT feel like a corporate task manager wearing a fantasy skin.

The visual direction is a polished modern mobile UI combined with old-school 8-bit/16-bit fantasy RPG aesthetics inspired by early console RPGs. Use original pixel-art styling and generic fantasy concepts; do not copy protected Final Fantasy or D&D assets, names, artwork, or lore.

The product name is:

Chores Your Own Adventure

Use CYOA as an internal shorthand where useful.

The primary branding icon should be a pixel-art crossed sword and broom crest.

⸻

CORE PRODUCT PHILOSOPHY

The app is designed around positive reinforcement.

Do not implement punishment mechanics.

There should be:

* no XP loss;
* no Gold loss for missed chores;
* no level loss;
* no streak-breaking punishment;
* no “failure” fanfare;
* no giant backlog when recurring chores are paused or missed.

If a timed quest expires, it simply becomes unavailable.

The core loop is:

Complete real-life quest → earn XP + Personal Gold + Party Gold → level up → unlock equipment/pets → customize character → progress toward Party Goals.

Keep interactions short and satisfying.

⸻

TECHNICAL DIRECTION

Build this as a proper full-stack PWA with persistent backend storage.

Use a robust relational data model.

Use server-side validation and server-side reward calculations for anything involving:

* XP;
* Gold;
* Party Gold;
* purchases;
* quest completion;
* verification;
* Legendary completion;
* Boss bonuses;
* Party Goal progress.

Never trust the browser/client to award its own currency.

All important reward/purchase operations must be atomic and idempotent.

Double taps, retries, reloads, or poor connectivity must never award rewards twice.

True real-time multiplayer updates are NOT required in V1.

Refresh relevant data when:

* a page loads;
* the user navigates;
* an action completes;
* the app regains focus where practical.

Design the schema so future expansion is easy.

QUEST TYPES

Support three core quest types.

1. Individual Quest

Assigned to one user.

Allow a Party Leader to select multiple users when creating an Individual Quest.

If multiple users are selected, create independent quest assignments for each user.

Do NOT turn this into a Party Quest.

Example:

Brush Teeth assigned to Jensen and Juliette creates two independent quest instances.

2. Open Quest

Visible to eligible Party members.

An Adventurer can claim only one Open Quest at a time per Party.

Once claimed, it becomes unavailable to others.

The Adventurer may release it freely before completion/submission.

No penalty for release.

Party Leaders do not need the same one-claim restriction.

3. Party Quest

A shared task with multiple assigned participants.

Each participant marks their own part complete independently.

Each participant receives normal individual rewards when they complete their own part.

The Party Quest completes once all required participants complete their portions.

Optionally award a small Party Quest completion Party Gold bonus when everyone finishes.

Verification, if enabled, is handled by Party Leaders.

XP AND LEVELS

XP is global and permanent.

Never spend XP.

Never lose XP.

Maximum V1 level:

Target pacing:

* first levels should come quickly;
* Level 10 approximately first month;
* Level 20 approximately 2–3 months;
* Level 50 approximately 8–12 months;
* Level 100 approximately 18–24 months of consistent participation.

Assume an active user may complete approximately 30–45 quests per week.

Expected approximate XP earning:

700–1,000 XP/week.

Create a configurable level curve.

Do not hard-code a brittle formula into UI components.

Store lifetime XP.

Store highest level achieved.

If the XP curve is later rebalanced, never reduce someone below their highest level previously achieved.

At Level 100:

Whenever choosing between a clever fantasy mechanic and a simpler user interaction, favor the simpler interaction.
